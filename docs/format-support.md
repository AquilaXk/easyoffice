# 포맷 지원 범위

포맷별로 읽기, 쓰기, 왕복 보존, 경고만 내는 항목, 거부 상한을 정리한 표입니다. 근거는 코드 파일 경로와 [policy-decisions.md](policy-decisions.md)의 PD 항목입니다. 코드나 PD에서 확인하지 못한 칸은 "미확인"으로 두었습니다. 마지막 대조는 2026-11-26입니다.

용어는 다음처럼 씁니다.

- **왕복 보존**: 열고 같은 형식으로 저장했을 때 값과 서식이 남는 항목.
- **경고만 내는 항목**: 저장·열기를 거부하지 않고 빠진 것의 종류와 개수를 상태줄과 응답 `warnings`로 알리는 항목.
- **거부 상한**: 넘으면 파일 전체를 거부하는 한도(Fail-Closed). 거부 오류는 `ResourceBudgetExceeded` 등으로 돌아옵니다.

XLSX·XLS·ODS의 읽기·쓰기는 엔진 자체 코덱입니다. 읽기 크레이트는 값·수식·서식 일부만 읽고, 이 표의 왕복 보존 항목 중 조건부 서식·유효성·슬라이서·차트 읽기·메모·시트 보호·화면 설정은 읽지 않으며 시트 전체를 한 덩어리 `Range`로 할당합니다. 그래서 코덱을 크레이트로 바꾸지 않았고, 대조표와 이유는 PD-269(2단계)에 있습니다.

HWP 5.0·HWPX의 읽기와 쓰기도 엔진 자체 코덱입니다. 편집기 파서를 같은 프로세스에서 열면 상한이 모자랍니다. 4바이트 빈 레코드 6천 7백만 개가 든 2.6 MB HWP 파일이 상주 메모리 4.3 GB를 씁니다. 엔진 상한 안인 문단 20만 개의 HWP는 쪽 배치까지 60초가 넘게 걸립니다. 압축비 100:1 안인 1 MB HWPX는 34초가 걸립니다. 편집기가 쓰는 OLE2 컨테이너 크레이트는 두 스트림이 같은 섹터를 가리키는 파일도 그대로 읽습니다. 엔진 `Hwp5Codec`의 구조와 `RichDocument`에 대응하는 편집기 모델도 없습니다. 그래서 교체를 보류했고, 합격선 시험은 `hwp_reader_boundary_pd269.rs`, 대조표와 실측은 PD-269(5단계)에 있습니다.

## 8. 이 문서에서 미확인으로 남긴 것

- DOCX, ODT, ODP, RTF의 포맷별 개수·크기 상한은 공통 상한 외에 코드에서 확인하지 못했습니다.
- HWP 5.0 편집기의 항목별 왕복 보존 범위는 rhwp 엔진이 정하며 이 저장소에서 목록으로 확인하지 못했습니다.
- ODT와 ODP의 "경고만 내는 항목"은 PD에서 포맷별로 적힌 것을 찾지 못했습니다.
- XLSX의 셀 수 상한은 `xlsx_*` 모듈에서 확인하지 못했습니다.
- 외부 프로그램이 만든 실제 파일의 호환성은 측정하지 않았습니다([performance.md](performance.md)의 "비교의 한계").
