# 성능 측정과 병목 (참조 앱 대비, 경로별 프로파일)

이 문서는 측정 결과와 최적화 후보를 적는다. 셸 PDF 내보내기의 후보 2·3·4와 병목 1~4는 PD-163으로 처리했고 결과는 4.1절에 있다. 문서→PDF 경로(PD-167)의 측정은 4.2절에 있다. 병목 10(ODS 열기)과 후보 8, DOCX·ODT·HWPX·XLSX 열기의 XML 읽기는 PD-168로 처리했고 결과는 4.3절에 있다. 시트 조건부 서식·데이터 유효성 평가(PD-171)의 측정은 4.5절에, 열기 응답 JSON·안전 XML 검사·엄격 JSON 파서(PD-186)는 4.6절에, WebUI 화면 경로(시트·문서·슬라이드)의 측정과 개선은 4.7절에 있다. 엔진 `--self-test` 벤치마크의 2026-11-20 측정과 이전 값 비교는 7절에 있다. CI의 Node 시험 시간 측정과 개선(PD-370)은 9절에 있다. 나머지는 아직 구현하지 않았다. 아래 수치는 모두 이 저장소의 측정 하네스로 직접 잰 값이고, 못 잰 것은 "못 잼"으로 적었다. 측정 기준 커밋은 `bac25cf`(main)이다. 그 뒤 main에 올라온 커밋(`f729ebb`까지)은 시트·XLS 저장, Pages 읽기, 웹 UI를 바꿨고 PDF·미리보기·Quick Look 경로는 건드리지 않아 다시 재지 않았다(XLS 저장·시트 정렬 값은 달라졌을 수 있다).

## 1. 측정 방법과 환경

### 환경

| 항목 | 값 |
|---|---|
| 기기 | Apple M4 Pro, 12코어, 24 GiB |
| OS | macOS 27.0.1 |
| Rust | 로컬 rustc 1.98.1(릴리스 CI 고정값은 1.93.1이라 같지 않음), `cargo test --release`(기본 release 프로파일, 디버그 정보 없음) |
| rhwp | 고정 커밋 `1a76570`(0.8.7). 참조 앱이 쓰는 rhwp도 같은 커밋이라 엔진은 같다 |
| 입력 | `third_party/rhwp/rhwp-studio/public/samples`의 HWP·HWPX, 합성 300쪽 보고서(`pdf_export.rs`의 `report_page_svg`), 엔진용 합성 문서·시트·슬라이드 |

**측정 중 다른 세션이 같은 기기를 썼다.** 1차 측정은 load average 12~35, 2차는 40~57이었다(12코어). 벽시계 시간은 부하에 따라 흔들리고, 특히 여러 스레드를 쓰는 우리 PDF 경로가 더 크게 흔들린다. 그래서 두 번 잰 값을 모두 적고, 2차부터 `time -l`의 CPU 시간(user+sys)을 함께 적었다. CPU 시간은 부하의 영향을 덜 받는다. 한 줄 요약의 비율은 "부하가 낮을 때 벽시계 비"와 "CPU 시간 비"의 범위로 읽어야 한다.

### 지표

- 시간: 케이스마다 새 프로세스를 5번 띄워 `total_ms`의 중앙값. 폰트 DB 만들기 같은 프로세스당 한 번 비용도 들어 있다(앱에서는 한 번만 낸다). 단계별(`phases`)도 중앙값.
- 최대 RSS: `/usr/bin/time -l`의 `maximum resident set size` 중앙값. 시험 바이너리 자체가 10 MB 안팎(Tauri 링크)이라 작은 문서의 RSS는 바탕값이 섞여 있다.
- 출력 크기: 결과 바이트.

### 참조 앱과 같은 조건으로 맞춘 방법

참조 앱은 GUI 앱이라 실행하지 않았다. 대신 그 Rust 쪽이 하는 일을 헤드리스로 다시 돌렸다. 두 가지 방식을 썼고, 두 값은 서로 맞아 떨어졌다(표의 `ref`와 `ref-repro`).

1. **참조 앱 사본에서 직접 빌드(`ref`)**: 사본의 문서 어댑터 크레이트와 `third_party/rhwp`(사본에서는 비어 있어 우리 고정 체크아웃을 연결, 같은 커밋)에 경로로 의존하는 일회용 하네스를 만들었다. 글꼴 대체 표(`pdf_font_fallbacks.rs`)와 Quick Look PDF 조립(`pdf.rs`)은 사본의 원본 파일을 그대로 포함했고, 문서 열기(`editable_core_from_bytes`: 파싱 후 `convert_to_editable_native`)와 `atomic_write`는 사본 코드를 옮겨 적었다. 참조 앱의 Quick Look은 `native-skia`(그래픽 라이브러리 바이너리를 내려받아 링크)로 빌드했다. 이 하네스는 참조 앱 이름이 들어가 있어 저장소에 넣지 않았다. 같은 `BENCH ...` 한 줄을 찍는 바이너리를 `--ref-bin`/`--ref-skia-bin`으로 넘기면 `bench-run.mjs`가 그대로 쓴다.
2. **저장소 안 재현(`ref-repro`)**: `perf_bench.rs`의 `ref:` 케이스가 같은 rhwp 호출 순서(`from_bytes` → `convert_to_editable_native` → `render_page_svg_native` → `svgs_to_pdf_with_options`)를 돌린다. 글꼴 대체는 우리 `add_font_fallbacks`를 쓴다.

### 비교의 한계

- 참조 앱의 홈 미리보기는 첫 쪽 SVG 문자열까지만 만들고 래스터는 웹뷰가 한다. 우리는 Rust에서 PNG까지 만든다. 그래서 미리보기 행은 같은 일이 아니다(아래 표에 따로 적음).
- 저장 검증은 범위가 다르다. 참조 앱은 저장 바이트를 rhwp로 다시 파싱하고, 우리는 컨테이너 구조만 검사한다(`save_verify.rs` 머리 주석). 빠른 것이 곧 더 좋은 것은 아니다.
- 한글 편집기(쪽 SVG 생성)는 두 앱 모두 웹뷰 안의 같은 rhwp wasm이라 비교하지 않았다. 웹뷰·WebKit 구간은 못 잼.
- Quick Look 시험은 앱 번들 밖에서 도는 헤드리스 호출이라 번들 글꼴(`pdf-fonts`)이 없고 시스템 글꼴만 쓴다. 번들 글꼴이 있을 때의 수치는 못 잼.
- 엔진 입력(DOCX·XLSX·PPTX·ODF·PDF 등)은 이 저장소의 인코더로 만든 합성 파일이다. 실제 사용자 문서(DOCX·XLSX·PPTX·PDF 원본)는 저장소에 없어 못 쟀다. 외부가 만든 PDF를 여는 경로도 못 잼.
- Windows·Linux는 못 잼(macOS만).

## 2. 참조 앱 대비

판정은 중앙값 차이가 10%를 넘으면 빠름/느림, 아니면 같음으로 했고, 몇 ms 이하의 절대 차이는 측정 한계로 보고 같음으로 봤다.

#### 2.4.1 Quick Look 적용 결과 (병목 6·7·4, 후보 1·4·5, PD-165)

세 가지를 적용하고 같은 하네스(`scripts/bench-run.mjs --runs 5 --suite quicklook`, 별도 `CARGO_TARGET_DIR`, 5회 중앙값)로 다시 쟀다. 기기 부하가 높아 시간(wall)이 흔들려서 CPU 시간으로 본다. 번들 글꼴 없이 시스템 글꼴만 쓰는 헤드리스 호출이다.

1. `fonts.rs`가 글꼴 면을 프로세스당 한 번 매핑(`make_shared_face_data`, 셸의 `with_mapped_faces`와 같은 방식).
2. 미리보기 PDF가 글자를 글꼴 서브셋으로 포함(`embed_text: true`). 서브셋이 실패한 쪽만 윤곽선으로 다시 변환한다(셸 PDF의 PD-114 5와 같은 재시도).
3. 쪽 콘텐츠 스트림 deflate 수준 6 → 1(`vendor/svg2pdf`의 `ConversionOptions::compression_level`, 기본 6이라 셸 출력은 그대로).
4. (PD-163, 이 작업이 아님) `fill_fonts`가 글꼴 파일을 복사하지 않고 면 매핑을 공유(후보 3). 아래 RSS 표의 1~4번 열은 이 패치를 더한 값이다.

### 4.1 셸 PDF 내보내기 최적화 결과 (PD-163)

병목 1(글꼴 질의), 3(글꼴 파일 복사), 4(압축 수준)와 병목 2(쪽마다 면 파싱)를 다뤘다. 전(`base`)과 후(`final`)는 같은 입력에 같은 하네스(`perf_bench.rs`의 `pdf_doc`, 합성은 `pdf_svgs`)로 5번 돌린 중앙값이다. 두 바이너리를 번갈아 돌렸고 측정 때 기기 부하는 31~49였다(12코어). 그래서 CPU 시간(user+sys)과 최대 RSS를 근거로 하고, 벽시계는 참고만 한다. 생성 PDF는 전후가 바이트 단위로 같다(biz_plan, form-002, kps-ai, issue1949, KTX, 합성 300쪽을 sha1로 비교). 쪽 수, 글꼴 포함, 텍스트 추출, 래스터가 모두 같다.

|---|---:|---|---|---|
| shift-return.hwp | 1 | 20 → 20 ms | 44 → 19 MB | 27 → 24 ms |
| biz_plan.hwp | 6 | 190 → 140 ms (-26%) | 426 → 48 MB (-89%) | 81 → 67 ms |
| form-002.hwpx | 10 | 750 → 550 ms (-27%) | 738 → 92 MB (-88%) | 289 → 232 ms |
| kps-ai.hwp | 77 | 2250 → 1690 ms (-25%) | 829 → 182 MB (-78%) | 864 → 700 ms |
| issue1949 | 115 | 4210 → 3170 ms (-25%) | 439 → 201 MB (-54%) | 1893 → 1595 ms |

- **병목 1(질의 메모, `pdf_font_select.rs`)**: 표가 많아 글자 요소가 많은 문서(issue1949, kps-ai)에서 CPU 약 25% 감소. 요청 종류가 적은 합성 문서에서는 질의가 원래 작아 변화가 작다.
- **병목 3(글꼴 공유, `vendor/svg2pdf`)**: 최대 RSS가 54~89% 줄었다. 쪽마다, 스레드 4개마다 글꼴 파일(Noto Sans KR 등) 전체를 복사하던 것이 RSS의 대부분이었다. 2.1절의 참조 앱 RSS와 견주면 모든 입력에서 우리가 작아졌다(shift-return 19 vs 35, biz_plan 48 vs 207, form-002 92 vs 247, kps-ai 182 vs 385, issue1949 201 vs 214, KTX 137 vs 310, 합성 71 vs 97 MB).

- **병목 4(압축 수준)는 바꾸지 않았다**. 수준별 CPU(ms)와 출력 크기(바이트), 5회 중앙값, 수준 6이 현재 값이다.

  수준 1이 가장 빠르지만 줄어드는 CPU는 2~9%이고 PDF는 18~25% 커진다. 수준 2~4는 수준 6과 CPU가 같거나 오히려 느린 값도 나온다(측정 노이즈). 근거가 부족해 6을 둔다.

### 4.2 문서→PDF: 엔진 작성기와 HWPX 쪽 배치 (PD-167)

| 작은 MD | 2 → 2 | 0.2 → 75 ms | 100 ms | 11 → 45 MB | 16 → 55 KB |
| 작은 TXT | 1 → 2 | 0.2 → 59 ms | 60 ms | 11 → 34 MB | 12 → 37 KB |

- 셸 경로의 시간 중 글꼴 DB 로드가 20~26 ms(프로세스당 한 번)이고, 큰 문서는 428쪽의 레이아웃·SVG 그리기·PDF 변환이 대부분이다. 쪽당 CPU는 약 35 ms로 4.1절의 HWP 문서(쪽당 22~27 ms)보다 조금 크다(합성 문서가 쪽마다 글자가 빽빽하다). PDF가 큰 것은 쪽마다 글꼴 부분집합이 들어가기 때문이고(PD-114와 같음), 글자가 글꼴 글리프로 들어가 검색·복사가 된다.
- **그리기와 변환 겹치기(`doc_pdf.rs`)**: 처음에는 한 스레드가 16쪽을 그린 뒤 변환했다. SVG 그리기(rhwp, 스레드 하나)와 변환(스레드 4개)이 서로를 기다렸으므로, 그리는 스레드를 따로 두고 길이 1의 채널로 변환 스레드에 넘기게 했다. 큰 DOCX 5번 번갈아 돌린 중앙값: 벽시계 6.7 → 5.1 초(-24%), CPU 18.0 → 17.4 초, 최대 RSS 349 → 374 MB(+25 MB, 미리 그려 둔 16쪽 한 묶음). 생성 PDF는 바이트 단위로 같다(큰 DOCX와 작은 DOCX를 `cmp`로 비교).
- 충실도는 같은 입력의 엔진 PDF와 셸 PDF를 `pdftoppm`으로 그려 눈으로 비교했다(이미지는 저장소에 두지 않았다).

### 4.5 시트 규칙 평가 결과 (PD-171)

시트 하나의 조건부 서식 규칙을 엔진 세션이 평가한다(`crates/easyoffice-sheet/src/rules/`). 셀 모양은 팔레트와 u32 단어 열(base64)로 보내고, 편집 뒤에는 바뀐 셀만 다시 판정해 달라진 셀만 돌려준다.

측정: 숫자 10만 셀(A1:J10000, 0~999 난수)에 규칙 5개를 모두 같은 범위에 걸고 `rules`로 한 번 설정(전체 평가)한 시간과 응답 바이트, 이어서 무작위 셀 1개를 바꾼 `apply` 30번의 중앙값. 기기 부하가 10~15였고(12코어) 세 번 잰 값의 폭을 적었다. `cargo test -p easyoffice-app --release --lib -- --ignored --nocapture rules_bench`.

| 규칙 5개 | 전체 평가(`rules`) | 응답 | 셀 1개 편집 | 편집 응답 |
|---|---:|---:|---:|---:|
| 셀 값 > 900, 상위 10, 3색 색조(최소·50백분위·최대), 데이터 막대(최소~최대), 아이콘 3개(33·67%): 범위 통계를 읽는 규칙 | 21~22 ms | 2,133,677 B | 8.8~9.0 ms | 170 B |
| 셀 값 > 900, 셀 값 사이, 3색 색조(숫자 0·500·1000), 데이터 막대(0~1000), 아이콘 3개(333·667): 자기 셀 값만 읽는 규칙 | 20~22 ms | 2,133,382 B | 0.01 ms 미만 | 170 B |

- 증분 전(편집마다 모든 규칙을 다시 평가하는 방식)의 편집 비용은 전체 평가와 같은 약 21 ms다. 통계를 읽는 규칙은 범위 통계를 한 번(10만 셀 훑기와 정렬본) 다시 만들어 2.4배 빨라지고, 자기 셀 값만 읽는 규칙은 바뀐 셀만 판정해 3자릿수 이상 줄어든다.
- 응답 2.13 MB는 칠해진 10만 셀 전부(셀당 평균 21 B)다. 같은 내용을 셀마다 JSON 객체(`{"ref":"A1","bg":"#RRGGBB","fg":"#RRGGBB","fl":3,...}`)로 보내면 약 8.94 MB로 추정한다(4.2배). 색은 팔레트에 한 번만 있고 셀은 2~4개 단어(8~16 B)다.
- 범위 통계(최솟값·최댓값·합·정렬본·표준편차)는 범위 목록당 한 번 만들어 규칙들이 나눈다. 위 첫 줄에서 4개 규칙이 한 번 훑은 값을 같이 쓴다.
- 식 규칙과 수식 피연산자는 어느 셀이 바뀌어도 규칙 전체를 다시 계산한다(읽는 셀을 모른다). 이 경로는 위 표에 넣지 않았다.
- 못 줄인 것: 통계를 읽는 규칙의 편집은 범위 크기에 비례한다(바뀐 셀이 최솟값·최댓값을 바꾸지 않으면 그 셀만 판정해도 되지만 아직 구현하지 않았다).

변경 4가지:

1. **열기 응답을 한 버퍼에 바로 씀(`convert_open.rs`)**: 문단·셀마다 `String`을 만들고 `join`·`format!`으로 3~4번 복사하던 것을 한 `String`에 직접 쓴다. 클리핑을 위해 워크북 전체를 `clone`하던 것도 없앴다(범위 밖 셀은 세고 건너뜀). 스타일이 없는 시트는 셀 해시 집합을 만들지 않는다(스타일 있는 셀만 기억). A1 주소는 `write_a1`로 버퍼에 쓴다. 이 변경만으로 열기 전체가 DOCX 531 → 404 ms, XLSX 408 → 256 ms(최대 RSS 683 → 498 MB, 315 → 127 MB).
2. **안전 XML 검사(`XmlSanitizer::validate_safe_xml`)**: `<`를 찾아 다음 글자를 보던 것을, 드문 `!`를 32바이트(워드 4개)씩 찾고 앞 글자가 `<`인지 보는 방식으로 바꿨다. 80 MB XML 한 번이 약 73 → 2 ms. `find_byte_swar`는 64바이트 안에 못 찾으면 넓은 모드로 넘어가므로 `<`·`"`처럼 흔한 글자를 찾는 호출자는 그대로다. `<!ENTITY`·`<!DOCTYPE` 거부 조건은 같다(`xml_scan_equivalence.rs`가 바이트 단위 기준 구현과 4만 개 무작위 입력으로 대조).
3. **같은 엔트리의 이중 검사 제거**: DOCX·ODT·HWPX는 `validate_zip_xml_entries`로 모든 XML 엔트리를 검사한 뒤 읽을 엔트리를 다시 UTF-8 검사하고 다시 스캔했다. 이제 `checked_zip_xml_entries`가 검사한 `(경로, 텍스트)`를 돌려주고 읽기가 그것을 쓴다(검사는 컨테이너 전체에 한 번, 순서 그대로). 저장 뒤 확인용 해석(`UniversalFormatConverter::decode`)의 HWPX 248 → 124 ms, DOCX 344 → 287 ms.
4. **엄격 JSON 파서의 중복 키 검사(`strict_json.rs`)**: 객체마다 `HashSet<String>`을 만들고 키를 복제하던 것을, 16개 키까지는 직접 비교하고 넘으면 그때 집합을 만든다(넓은 객체도 선형). 셀 104만 개(35 MB) JSON 파싱 147 → 78~94 ms. 중복 키 거부 규칙은 같다.

적용하지 않은 것(측정으로 5% 미만이거나 결정이 필요함):

- **저장 뒤 확인용 해석**(`conversion_response`의 `decode`)은 저장 시간의 18~46%(HWPX 138 ms/303, DOCX 50/131, XLSX 84/457)다. 쓴 바이트가 다시 열리는지 확인하는 검증이라 줄이지 않았다. 더 빠른 읽기(`decode_rich`)로 바꾸면 `paragraphCount`·`tableCount`가 달라질 수 있어 결정이 필요하다.
- **XLSX 저장**의 `build_sheet_xml` 57 ms 중 스타일 없는 시트의 해시 집합과 수식마다 `escape` 복사는 약 20 ms(저장의 4%)라 건드리지 않았다. 같은 이유로 `parse_sheets`의 `BTreeMap`도 그대로다.
- **PDF 내보내기의 글꼴 표 파싱**(4.1절 병목 2, CPU의 약 22%)은 SVG 파서 크레이트 사본이 필요해 PD-163의 결정 대기 그대로다. 셸 미리보기(27~109 ms)·카드 그림(KTX 90 ms)·77쪽 PDF(658 ms)는 이번에 다시 쟀고 rhwp 파싱과 렌더러가 대부분이라 바꾸지 않았다.
- **통계를 읽는 조건부 서식 규칙이 있는 시트의 셀 하나 수정**(60만 셀에서 43 ms)은 4.5절의 보류 그대로다.
- `SheetEngine::sort_rows`(10만 행 400 ms)는 앱의 어느 명령도 부르지 않아(시험·자체 점검만) 고치지 않았다. 필터는 엔진에 없다(페이지가 처리).
- PDF 편집 검사(`pdf_inspect`)와 카드(`pdf_card`)는 9.1 MB 텍스트 PDF에서 4.8 ms와 10 ms로 이미 작다.
- 못 잼: 시작 창 미리보기·Quick Look을 4.1~2.4절 이후 다시 잰 값(바꾼 코드가 없음), 실제 사용자 파일, Windows·Linux, 화면(웹뷰) 구간.

### 4.7 WebUI 화면 경로 (시트·문서·슬라이드)

엔진이 아닌 `crates/easyoffice-app/ui`의 화면 비용이다. 하네스는 `scripts/bench-webui.mjs`다(헤드리스 브라우저와 실제 엔진 `--serve`, 입력은 CDP 이벤트). 한 줄이 사용자 동작 하나이고, 값은 브라우저가 알려 주는 주 스레드 점유 시간(`busy`), 화면까지 걸린 벽시계(`wall`), 레이아웃·스타일 재계산 횟수와 DOM 노드·JS 힙이다. `--profile`을 주면 동작마다 자기 시간이 큰 함수를 찍는다.

```bash
node scripts/bench-webui.mjs --app <easyoffice-app> --chrome <브라우저> --only sheet --rows 25000 --cols 20
node scripts/bench-webui.mjs --app <easyoffice-app> --chrome <브라우저> --ui <전 ui 디렉터리>   # 같은 시나리오를 다른 체크아웃에
```

환경: Apple M4 Pro, 같은 엔진 바이너리(perf/engine 릴리스 빌드)를 전·후에 썼다. 전은 `origin/main`의 `ui/`, 후는 이 브랜치다. 측정 중 다른 작업이 기기를 같이 썼고 값은 한 번 잰 것이다(수십 ms 이하 차이는 잡음이다).

**규모.** 구조화 저장은 항목 50만 개(`MAX_STRUCTURED_ITEMS`)까지라 저장할 수 있는 시트는 약 50만 셀이다. 요청한 10만 행 × 20열은 200만 셀이고 엔진 세션 상한(200만)에 딱 걸리며, 이 크기에서는 사본 한 번이 500 MB를 넘고 편집 때 전체 시트를 다시 보내는 경로가 쓰인다. 그래서 두 규모를 모두 적는다.

| 시트 동작 | 25,000행×20열(50만 셀) 전→후 | 100,000행×20열(200만 셀) 전→후 |
|---|---:|---:|
| 열기(엔진 해석 포함, 첫 그리기까지) | 2,987 → 1,980 ms | 14,836 → 10,346 ms |
| 셀 하나 편집 + Enter(화면 갱신까지) | 1,704 → 308 ms | 6,408 → 2,363 ms |
| 수식이 읽는 열의 셀 편집 | 1,634 → 280 ms | 4,444 → 3,167 ms |
| Shift+아래 화살표 한 번(큰 범위 집계) | 100 → 16 ms | 627 → 16 ms |
| Ctrl+A 집계 | 459 → 149 ms | 2,549 → 2,598 ms |
| 조건부 서식 규칙 걸기 | 1,357 → 465 ms | 1,566 → 1,248 ms |
| 되돌리기(Ctrl+Z) | 1,660 → 366 ms | 5,178 → 4,376 ms |
| 정렬(내림, 전체) | 800 → 590 ms | 7,186 → 5,346 ms |
| 스크롤 10행씩 30번(1회당) | 약 16 ms(프레임 한계), 변화 없음 | 같음 |

스크롤은 이미 가상화돼 있다(DOM 셀 680~1,200개, 100만 행 높이는 스페이서). 필터는 화면에 기능이 없어 재지 않았다.

| 문서·슬라이드 동작 | 전 → 후 |
|---|---:|
| DOCX 1만 문단(약 280쪽)에서 글자 1개 입력, 핸들러 비용만(동기) | 44.6 → 7 ms |
| 같은 입력을 CDP로 넣고 프레임 두 번까지 | 85 → 48 ms |
| DOCX 열기 | 417 → 420 ms(첫 레이아웃 190 ms가 대부분) |
| 실제 쪽 나눔(PD-200) 뒤 같은 DOCX 1만 문단: 열기 / 글자 1개 입력(프레임 두 번까지) / 핸들러만 | 545 → 488 ms / 48.4 → 43.9 ms / 8.1 → 8.5 ms(쪽 나눔 모듈은 첫 계산 약 70 ms, 입력 1회 약 3 ms) |
| 찾기(2글자)·다음·모두 바꾸기 | 변화 없음(색인 기반이고 레이아웃이 비용) |
| PPTX 300장 썸네일 목록에서 슬라이드 선택(주 스레드 점유) | 27.7 → 4.7 ms |
| 슬라이드 제목 입력 뒤 썸네일 갱신(1.5초 구간 점유) | 29 → 9 ms |
| 메뉴 9개 차례로 열기(1개당 주 스레드) | 1.8 ms, 변화 없음. 30번 열고 닫아도 리스너·노드 증가 없음 |

원인과 고친 곳:
- 셀을 옮길 때마다 `Object.keys(시트 전체)`로 항목 수를 세던 선택 집계(`sheet-input.js`)와 서식 상태(`sheet-format.js`)가 범위가 작으면 주소로 읽는다. 결과는 같고 순서만 달라질 수 있는 합계는 표시가 유효숫자 12자리라 같다.
- 수식 결과를 반영할 때 수식 셀마다 `document.querySelector('td[data-cell=...]')`로 화면 전체를 훑던 것(수식 10만 개면 편집마다 0.5 s)을 인덱스 조회만 남김(`sheet-controller.js`).
- 문서 입력마다 문서 전체 DOM을 직렬화하던 저장본을 "낡음 표시"로 바꾸고 다음에 읽을 때 한 번만 직렬화(`workspace-panels.js`의 `docTabStore` 접근자). 되돌리기·자동 저장·모듈 전환이 읽는 시점에 같은 내용이 나온다.
- 큰 시트(셀 2만 개 초과) 자동 저장이 건너뛰기 전에 시트 전체를 복사하고 키를 두 번 세던 것을, 복사 전에 첫 2만 번째 셀에서 멈추는 검사로 바꿈(`workspace-session.js`).
- 열기 직후 기준값(편집 여부 비교용)을 키 정렬한 복사본의 JSON 해시에서 셀별 해시의 합으로 바꿈(순서 무관, 빈 셀 무시는 그대로, 시험 `test-webui-perf-equivalence.mjs`가 이전 구현과 같은 판정을 하는지 400쌍으로 견줌).
- `normalizeFormattedNumericCell`이 쉼표·퍼센트·통화 기호가 없는 문자열에서 정규식 3개를 돌리지 않음(같은 결과를 5천 개 생성 입력으로 견줌).
- 슬라이드 썸네일은 장 수가 같으면 버튼을 재사용하고 바뀐 것만 쓴다(선택·입력 때 300개를 새로 만들던 것 제거).
- Base64 변환의 청크 대체 경로 4곳(`file-open.js`, `hwp-session.js`, `hwp-host.js`, `pdf-edit.js`)을 `sheet-utils.js`의 `bytesToBase64`로 모음.

처리하지 않은 것(근거):
- 편집·정렬·되돌리기에 남은 비용의 큰 부분은 되돌리기 사본의 시트 전체 복사(`cloneSheetStore`, 50만 셀에서 약 100~200 ms, 200만 셀에서 약 0.5 s)다. 항목 객체를 공유하는 구조로 바꿔야 줄고, 항목을 제자리에서 고치는 곳이 많아 이번에 바꾸지 않았다. 문자열·객체 생성 변형 3가지(키 목록, `for in`, 스프레드)는 모두 같은 시간이라 5% 미만으로 버렸다.
- 편집 때마다 엔진 세션과 맞추는 전체 비교(`diffAgainstMirror`, 200만 셀에서 약 0.5 s)는 바뀐 셀 목록을 호출부가 넘겨야 한다. 사본 교체·되돌리기 같은 경로의 어긋남을 이 전체 비교가 바로잡고 있어 이번에 건드리지 않았다.
- 되돌리기 사본은 64단계까지 쌓였고 200만 셀 시트에서 편집을 거듭하면 JS 힙이 2.5 GB까지 올라갔다. PD-221에서 시트 변경은 바뀐 칸만 담는 기록(100단계, 192 MiB)으로 바꿨다(한 단계 143.6 MB → 0.01 MB 미만, `scripts/bench-sheet-undo.mjs`).
- Ctrl+A 집계는 사용 범위 크기에 비례한다(50만 셀 149 ms, 200만 셀 2.6 s). 증분 집계가 필요하다.
- 문서 열기는 문단 1만 개의 첫 레이아웃(190 ms)이 비용의 반이고 브라우저 몫이다.

## 6. 못 쟀거나 더 해야 할 것

- 실제 사용자 DOCX·XLSX·PPTX·PDF와 외부가 만든 PDF 열기, Pages 파일 열기.
- 번들 글꼴이 있을 때의 Quick Look, Windows·Linux, 웹뷰 구간, 한글 편집기 안의 쪽 SVG 생성.
- 최대 RSS가 컸던 원인은 쪽·스레드마다 한 글꼴 파일 전체 복사가 대부분이었다(4.1절에서 제거). 남은 RSS(전 면 매핑, 병렬 스레드, 쪽 객체)의 분해는 하지 않았다.
- 줄 단위 핫스팟(디버그 정보 없이 `sample`만 사용). 줄이 필요하면 `CARGO_PROFILE_RELEASE_DEBUG=line-tables-only`로 따로 빌드해야 한다(전체 재빌드).
- 벽시계 값은 측정 중 기기 부하의 영향을 받았다. 낮은 부하에서 다시 재면 우리 쪽 벽시계 수치는 더 낮아질 가능성이 크다(1차와 2차 차이로 보인다).

## 7. `--self-test` 벤치마크 (2026-11-20)

엔진의 결정론적 벤치마크(`crates/easyoffice-app/src/benchmark*.rs`)를 `cargo run -p easyoffice-app -- --self-test`로 돌린 값이다. 각 스위트는 기준 구현과 최적화 구현을 같은 입력으로 5라운드 교대 실행하고(`bench_rounds=5`) 두 결과가 같은지(`eq=true`)를 먼저 검사한다. 속도 하한은 release에서만 판정한다(PD-082, `benchmark_large.rs`의 `performance_gate`).

### 8.6 한계

- 크기는 macOS arm64만 쟀다. 다른 OS의 실행 파일 구성은 설치본 크기와 deb 안의 파일 크기로만 짐작했다.
- `cargo bloat`의 크레이트별 값은 심볼 이름으로 나눈 추정이다(제네릭 인스턴스는 호출한 쪽이 아니라 정의한 크레이트로 센다).
- Quick Look 크레이트 빌드가 이 기기에서 한 번 `can't find crate`(proc-macro dylib을 못 불러옴)로 죽었다. 같은 `strip = "debuginfo"` 프로필로 다시 여덟 번(문자 코덱 크레이트 하나만 일곱 번, 전체 한 번) 빌드했을 때는 모두 성공했고 원인은 확인하지 못했다. 방어로 두 `Cargo.toml`에 `[profile.release.build-override] strip = "none"`을 뒀다(PD-293). 8.4절의 Quick Look 값은 첫 실패 뒤 `CARGO_PROFILE_RELEASE_STRIP=none`으로 빌드한 정적 라이브러리를 `swiftc`로 묶은 결과다.

### 9.3 개선(하니스 DOM, 시험 파일은 그대로)

`scripts/webui-dom-harness.mjs`와 `scripts/webui-css-selector.mjs`만 바꿨다. 선택자 문법과 일치 규칙은 같고 시험 파일의 단언은 하나도 약해지지 않았다.

1. 같은 `class` 문자열의 토큰 집합을 공유한다(변경 메서드는 복사 뒤 쓴다).
2. `querySelector`는 첫 일치에서 멈춘다. 선택자 목록은 요소마다가 아니라 질의마다 한 번 찾는다(`compileSelectorList`). 클래스 선택자는 `class` 문자열에 부분 문자열이 있는지 먼저 본다.
3. 질의 결과를 루트와 선택자별로 기억한다. 문서 안에서 요소의 부모가 바뀌거나, 그 선택자가 읽는 속성(`id`·`class`·`[name]`, `:not()` 안쪽 포함)의 값이 바뀔 때만 무효로 만든다. 문서 밖 트리의 변경과 문서 밖 루트의 질의는 기억하지 않는다. 호출자는 매번 새 배열을 받는다.
4. 새 시험 `scripts/test-webui-dom-query-cache.mjs`가 변경 종류마다(클래스·속성·`id`·`dataset`·`appendChild`·`insertBefore`·`removeChild`·`replaceChildren`·`innerHTML`·`textContent`·복제·직접 `parentElement` 대입)와 난수 변경 120단계마다 기억한 답이 새로 훑은 답과 같은지 비교한다. 무효화 코드를 일부러 지우면 이 시험이 실패하는 것을 확인했다.

| 보드 카드 찾기(노드 300개, 지금 식 대 id 선택자) | 0.03 대 0.01 미만 | 0.04 대 0.01 |

코파일럿 실제 조작은 단계마다 `PRESS_MS` 90 ms·`DRAG_MS` 380 ms·`EXPECT_MS` 대기(25 ms 간격)가 들어 있다. 보드 카드 찾기는 한 단계에 대여섯 번 불려도 0.2 ms 미만이라 단계 시간(수백 ms)에 비해 보이지 않는다. 열 전체를 훑는 필드·책갈피 읽기는 6 ms 안쪽이라 대화상자가 열릴 때 한 번 드는 값이다. 선택자와 DOM 읽기는 줄이지 않고 그대로 둔다.

### 10.3 경량화

**`rhwp_bg.wasm`에 `wasm-opt`(binaryen 132, npm 판은 Node에서 도는 같은 결과의 도구)**: 이득이 없어 넣지 않았다.

| 설정 | 크기 | brotli(q11) | 걸린 시간 |

| `-Oz --converge` | 11,711,809 B (-0.93%) | 3,116,859 B (-0.28%, -8.8 KB) | 7분 |

고정 산출물은 이미 최적화돼 있다(코드 10.2 MB, 데이터 1.58 MB). 3.13 MB 번들에서 9 KB를 얻으려고 104 MB의 npm 의존, 7분짜리 단계, 해시·출처 기록의 변경을 들일 값이 아니다.

**PDF 번들 글꼴 TTF 제거**: 편집기 번들의 `NotoSansKR-Regular.woff2`(562,220 B)를 실행 파일에 내장된 자산에서 읽어 메모리에서 푼다(`pdf_font_face.rs`, `wuff` 0.2.10, MIT, 이미 쓰는 `brotli-decompressor`·`bytes`만 끌고 온다).

|---|---|---|
| 설치본의 `pdf-fonts/NotoSansKR-Regular.ttf` | 2,519,996 B | 없음(OFL 문서 4 KB만) |

해독한 글꼴이 TTF와 같은지: 글리프 12,107개, 문자 11,708개(차집합 0), 글자마다 윤곽선 해시와 진행 폭이 모두 같았다(시험 `the_decoded_face_has_the_characters_outlines_and_advances_of_the_old_ttf`). 한글 PDF의 글꼴 이름·검색용 글자 지도(`<D55C>`·`<AE00>`)가 같고 크기 차이가 2% 안이다. 실행 파일에 내장된 자산에서 같은 바이트를 찾는 시험, 악의적 입력(잘림·서명 없음·4 GiB를 적은 머리·상한 초과·깨진 데이터) 시험이 있다. 입력은 4 MiB, 해독 결과는 16 MiB가 상한이고, 상한은 해독기가 출력 칸을 잡기 전에 머리의 `totalSfntSize`로 먼저 검사한다.

**UI 껍데기 크레이트에만 `opt-level = "s"`**: 이득이 없어 되돌렸다. `tauri`·`tauri-runtime(-wry)`·`tauri-utils`·`wry`·`tao`·`muda`·`rfd`·플러그인 4개·`tokio`·`reqwest`·`hyper` 계열 17개를 같은 소스로 `s`와 기본 수준으로 두 번 빌드했다.

| 구간 | 기본 | `s` | 차이 |
|---|---|---|---|
| 실행 파일 | 57,364,512 B | 57,378,480 B | +13,968 B |
| `__text` | 26,518,368 B | 26,283,092 B | -235,276 B |

코드는 0.9% 줄었지만 언와인드 표와 링크 편집 구간이 그만큼 늘어 파일 크기는 오히려 14 KB 커졌다. 예상한 -0.6 MB는 나오지 않았다.

**Windows·Linux 심볼 제거 폭**: 이 기기에서 크로스 빌드를 못 해서 `.github/workflows/size-probe.yml`(수동 실행)을 더했다. 각 OS에서 데스크톱 셸을 `strip = "symbols"`(배포)와 `strip = "none"`으로 두 번 빌드하고 두 크기와 차이를 잡 요약에 쓴다. 일반 CI와 릴리스는 이 잡에 기대지 않는다. 결과는 실행하면 8.4절에 옮긴다.

**글꼴 부분 집합화는 하지 않았다(위험 조사만)**
- OFL은 개조본에 예약 글꼴 이름(Reserved Font Name)을 쓰지 못하게 한다. 부분 집합은 개조본이다. 예약 이름이 나눔 글꼴 계열(`Nanum`, `NanumGothic`, `NanumMyeongjo` 등), `D2Coding`, `Pretendard`, `Spoqa Han Sans`에 걸려 있어서, 줄이면 글꼴 이름을 바꿔야 한다. 문서가 `나눔고딕`·`D2Coding`을 이름으로 부르므로 이름을 바꾸면 문서와 맞지 않는다.
- Noto Sans KR·Noto Serif KR·Gowun은 예약 이름이 `Source`(어도비)뿐이라 이름은 바꿀 필요가 없다. 대신 번들 글꼴이 이미 한국어 부분 집합이다(Noto Sans KR 문자 11,708개). 문서에 나오는 한자·가나·특수 기호를 더 빼면 글자가 사라져 대체 글꼴로 넘어간다.
- 번들 글꼴 합계 15.5 MB 중 D2Coding 둘이 3.46 MB다. 필요할 때 내려받는 안은 오프라인 우선 원칙과 어긋나서 QA 결정이 필요하고, 내려받기는 하지 않았다.
